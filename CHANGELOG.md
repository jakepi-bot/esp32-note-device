# Changelog

## unreleased

- **An idle Home stops waking once a minute: the band no longer draws a clock, and says `NO TIME` only while the clock has never been set.** Home's band carried `HH:MM`, and the 10 s facts poll set `DirtyClock` whenever the minute changed, so a resting device paid a CPU wake and a ~589 ms panel drive every minute (measured: one frame in 92 s, which defeated the idle state the same way the 30 s jobs did). `Snapshot::clock_text` and `Facts::clock` are gone; `UiState::set_facts` compares only `clock_set`, the one clock answer the band still draws, so a minute rollover is not a fact at all and the per-minute repaint path is deleted. The band's time slot carries `NO TIME` (7 columns, beside the 10-column queue slot) while the clock has never been set, and nothing once it has; the hero's `NO TIME` word moved into that slot, so the hero keeps answering what the device is doing and no slot restates another. No timer was deleted because there was none: the minute rode the existing 10 s `poll_facts`, and only the text comparison is gone. The upload bar and the recording counter are untouched event-driven paths; the internal wall clock, note and upload timestamps, and the `clock` console command are unchanged. Host cases in `hg_notes_ui_tests`: a minute rollover, however many polls, draws nothing; the warning appears and clears only on the `clock_set` answer, and is adopted off Home without a frame; the band case pins that no time text is drawn, that the warning takes the old slot, and that a full `99 TO SEND` still leaves a gutter before it. `ctest` 9/9, `hg_notes_ui_tests` 84 cases, 0 failed. Docs: [the spec](docs/notes-ui-spec.md) §3.2, §4.2, §4.3, §14 and §17.1, [as built](docs/notes-ui-implementation.md), [using the device](docs/notes-device.md).
- **A hand-over actually reaches the glass: the partial refresh writes the whole frame in the panel's own addressing, so Home -> menu -> list -> note draws in 589 ms instead of the 1.4 s full flash.** The partial-refresh change that made hand-overs `Refresh::Partial` was verified on the probe and visually wrong: the driver narrowed the update to a window over the rows that moved, and while a band up to half the page paints, a page-size band - every hand-over - painted nothing on this unit. The photographs showed three presses with no visible page and then a flash on the fourth, which is worse than the behaviour it replaced. The cause is the window's addressing, not the waveform: `update_once()` expressed the window 0 -> 199, which is not the form this panel accepts for a partial. Measured on the unit: the same `0x22 0xCF` trigger over a window written 199 -> 0 with the cursor on row 199 and the frame written forward paints a whole page in **589 ms**, and a 27-row bar move costs the same 589 ms, so narrowing the window never bought time in the first place. `EpdDisplay::update_once()` now writes the whole frame into `0x24` and the frame on the glass into `0x26` in `panel_init()`'s addressing (`EpdDisplay::partial_frame()`), triggers `0xCF` and waits on BUSY; the frame diff still decides *whether* an update is sent (a frame that changed no pixel costs nothing) and is still logged as a band for the bench. The full path, the first frame after boot, the sleeping face and `epd full` are untouched. Verified on the bench unit (firmware 0.7.1, flashed app-only at 0x20000, readback digest matched): the device's own log reads `partial 176 rows (8..183) of 200, 589 ms of driving` for a Home -> menu hand-over, three for three after a chip reset each, against the pre-fix 1,400-1,600 ms of drawing; key-to-first-change is unchanged at 200 ms; a walk of Home -> menu -> list -> note -> list -> menu -> Home photographs as six correct pages; after two hand-overs in a row the page is pixel-identical to the same page drawn with `epd full` (0.00 % of pixels moved, matching brightness histograms), so no grey residue accumulates; the boot frame still logs `full refresh`, and the `kFullEvery`/`kHandoverFullEvery` budgets are unchanged. `ctest` 9/9 (958 cases). Docs: [the spec](docs/notes-ui-spec.md) §1 and §15.1-15.2 (the band premise and its measurements), [as built](docs/notes-ui-implementation.md), [the modules](docs/firmware-modules.md).
- **The bench numbers for a hand-over, with the trap written down: it is 200 ms, and the 1.6 s reading was the fourth move.** `tools/latency_probe.py` now says in its docstring what cost an afternoon: only the first three hand-overs of a session are partial - the fourth `key hold` in a row spends the ghost budget (`kHandoverFullEvery = 4`) and draws the full waveform - so a number taken without resetting the board is the fourth move's, not the one a person waiting on the menu sees. Measured on the unit (`main` `b1e7e89`, flashed at `0x20000` and read back with `verify-flash`): with the board reset before each run, a BOOT hold on Home is **200 ms to the first pixel and one more frame to settle, ~200 ms of drawing** (three runs), against the pre-fix 200 ms / 1400 ms; five back-to-back holds read 0 ms, 0 ms, 0 ms, then **2000 ms** for the fourth, then the session carries on partial. Five holds in one session `epd ghost`-free is the ghost budget doing its job, not a regression.

- **Walking the device is quick now: a screen hand-over is a partial refresh, not a 1.4 s full flash, and the machine keeps its own ghost budget so the glass stays clean.** Home -> menu -> list -> note used to ask for `Refresh::Full` on every move, on the premise that a partial between two layouts that differ everywhere leaves the old one ghosted. That premise belonged to the driver before `82d6124`: `EpdDisplay::update_once()` now diffs the frame against what the panel was sent, pads the changed rows by two and drives only that window, so where the new page is white the rows the old page inked are re-driven to white in the same pass and rows that were paper on both pages are never driven at all - "clear only the region the previous page inked", done by the component that can see both frames. `ui_app.cpp` gains `handover()` (the moves in §13.2 that now carry `P`: Home <-> menu, menu <-> list, list <-> note, About, Unpair and the two confirms, each way) and `ScreenApp::handover_frame()`, which is where the ghosting control lives: a partial cannot *finish* a black -> white transition, so **the fourth hand-over in a row is a full refresh** (`kHandoverFullEvery = 4`, four times tighter than the driver's `kFullEvery = 10` because a hand-over leaves a whole layout's worth of residue). A menu session of any depth therefore carries at most three pages of ghost and sees one flash, on the fourth move; any full frame - a hero change, the sleeping face, `epd full` - resets the count, because that flash already cleaned the glass. One case is not a hand-over even though it is a move between the UI's own pages: a hero word that moved while another page was up (`READY` -> `UPLOADING` on the menu, an upload starting behind the glass) was never drawn, so the frame that returns Home stays full (`hero_stale_`) - otherwise the partial leaves the old word under the new one, the artefact §4.3 exists for. `press()`'s catch-all no longer says "any screen change is full": the class is the machine's answer, and the actions' own `Refresh` values for the runtime's faces are what remains. Full is deliberately kept for the cases where it is correct - the first frame after boot (`NotesUi::render`'s `first_frame_` and the driver's `!partial_`), the sleeping face, the busy face of a wipe or a format (it stands for 20-90 s, so one clean flash is nothing against the job) and the Home frame that ends it, the recording face and the player (the runtime starts and stops the codec, and a commit moves the counts under the frame), the pairing ask, the pages a port owns (Phone, Wi-Fi setup), a list rotation, a hero change, and `epd full`. Nothing waits on the panel that did not before: the driver's task still owns the BUSY wait, so the 200 ms key-to-first-change is untouched. Host cases in `hg_notes_ui_tests` (81 -> 83): a new `refresh: a hand-over is partial, and the fourth in a row spends the budget` walks the device and asserts P, P, P, F, P, P on the way in and out, then that the recording face and a pairing ask are still `F` and that `sleep_face()` is; a second, `refresh: a hand-over that returns to a stale hero is full` starts an upload while the menu is up and checks the frame that comes back to Home is `F` and the walk after it partial again; the eleven existing cases that asserted `F` on a hand-over now assert the class the walk actually draws, each with the cadence noted where the budget is what the case sees. `ctest` 9/9 (83 cases, 0 failed); `pio run -e notes` builds at 1,505,648 B with 64,048 B of static RAM (63 % of the `ota_0` slot free). Docs: [the spec](docs/notes-ui-spec.md) §13.2's transition table and a rewritten §15.1-15.3 (the old §15.1 claimed a partial re-drives the whole panel, which stopped being true in `82d6124`), [as built](docs/notes-ui-implementation.md), [using the device](docs/notes-device.md).

- **A note longer than five minutes actually uploads: a part's read is bounded to that part, and the part after an accepted one is read from a file that is still open.** The parts feature shipped and had never sent one part body: on the unit every attempt died before a request was opened with `cannot read recording.wav: stopped at 17247360 of 14400000 bytes`, and `part 0`'s share of a 359 s note (14,400,000 B) was met with the whole recording's PCM (17,247,360 B), so `audio_read_short` fired in the hash pass. **Two defects were stacked**, and the second only appeared once the first was fixed: `Uploader::step`'s hash and send passes called `std::fread(buf_, 1, kChunk, file_)` with nothing bounding it to `part_.audio_bytes`, and then, on the part being accepted, the answer's `close()` freed the `FILE*` before `begin_part()` seeked it — `fseek(NULL)` panicked the chip (`Guru Meditation … LoadProhibited`, `EXCVADDR 0x10`, backtrace `fseek` ← `Uploader::begin_part` ← `step` ← `Runtime::step_sync`) immediately after `part 1/2: HTTP 202 -> accepted`, so no segmented note could ever reach part 1 and the device rebooted into the same part again. Both reads now take `part_read_len(part_.audio_bytes, done, kChunk)` — an inline rule beside `audio_read_short`/`resume_index`, `std::min<size_t>(kChunk, part_bytes - done)`, one chunk and never past the part, zero once the part is read — and the body is read from `part_.audio_offset`, not from where the hash pass stopped (the single-part rewind to byte 0 only ever worked because a single-part note starts there). `close_transfer()` is the new seam: the POST's client is closed when an answer arrives, the recording is closed only when the note is over (`Step::Done`, a rejection, a retry, or `cancel()`), and `begin_part()` refuses a closed stream instead of passing NULL to `fseek`. Host case in `hg_epaper_notes_tests` (53 -> 54): `parts: a part's read stops at the part, not at the end of the recording` walks a 359 s recording's two parts one chunk at a time with the same numbers the unit printed — every read at most one chunk, never past the part, never into the next one, the parts ending exactly end to end, a part shorter than a chunk read in one go, a whole number of chunks ending on a zero-length read, and the unbounded whole-file read failing `audio_read_short` as it did on the board. `ctest` 9/9. Bench, on the unit (`pio run -e notes`, flashed at 0x20000, 1,485,367 B / 63,504 B static RAM), against a controlled collector that answers `/health` with `note_parts:1` and refuses part 1 once with `503`: the same 359 s / 16.4 MB note went out as part 0 = 44 + 14,400,000 B `202` and part 1 = 44 + 2,848,640 B (59.3 s) `503` → retried alone after 10 s with the same key and the same bytes → `200 duplicate`, `note … synced (HTTP 200)`, `notes status` `pending 0`, and the two part files reassemble to 17,248,640 B of PCM = 359.3 s, each part's declared `checksum` equal to the SHA-256 of the bytes it stored. The unit's card ended where it started (111 stored / 0 pending / 110 sent / 1 failed) with the real notes endpoint restored.

- **A note longer than five minutes uploads in five-minute parts and stays one note, and a part that fails retries alone.** The 248 MB note proved the upload works but not that it survives: one POST of 22 minutes (after a ~14 min hash pass) meant a drop at minute 80 cost the whole body, and every retry replayed it from byte 0. The device now plans parts from the WAV's own header (`plan_parts`, `kPartSeconds = 300` in `notes_queue.cpp`) and sends each as its own `POST /notes/v1`: a complete WAV of at most 300 s plus `note_id`, `part_index`, `part_count`, `part_offset`, `duration_seconds` = that part's own length, `checksum` = that part's digest, and `idempotency_key` = `<note_id>.<index>` (inside the contract's charset). The MAC covers the part fields (`|parts=1|<note_id>|<index>|<count>|<offset>` appended to the §2.2 canonical), and the schema is versioned (`kPartsSchemaVersion = 1`, `parts_version` in `note.json`). A note at or under five minutes — including exactly 5:00 — sends **exactly the v1 bytes**, no part fields, so an existing hub keeps accepting it. The hub (`plugin/notes_ingest.py` + a new `plugin/notes_parts.py`, which holds the one part rule both halves pin) keys a part by its note (`job_id = sha256(device_id|note_id)`, the same value a single-part note's key derives), stages the parts under `inbox/<job>/parts/` with a `manifest.json`, and streams them into one `recording.wav` when the set is complete (a 2 GiB note is never held in memory); `note.json` is written last — the commit point — and carries `note_id`, `part_count` and the per-part list, with `duration_seconds` the sum and `audio_sha256` the digest of the assembled file. A partial note is not an inbox note: it has no `note.json`, so the pipeline skips it rather than quarantining it, `/health` reports it as `partial` (with `note_parts:1` as the capability), and `sweep_parts` removes a set nothing finished after `PART_MAX_AGE_S` (24 h), logging `partial voice note <job> removed: N of M parts, …`. - **A note records until the card (or 2 GiB) fills, not for 15 minutes.** The device's `kMaxDurationS` is 86400 s (24 h) and its per-note ceiling `kMaxNoteBytes` is 2 GiB, which is 12.4 h of 24 kHz PCM16 mono; the byte cap therefore binds first and the duration cap is only a sanity bound. `note_max_s` (the recording-length setting) defaults to that same 86400 and its range is 10..86400, so out of the box nothing stops a note early - it was 300 s with a 10..3600 range, which is what actually ended a recording. `Capture::start` computes its byte budget in 64 bits (24 h at 48 KB/s is 4.1 GB, past a 32-bit product) and `Capture::finish` stops clamping `duration_s` at 900 s, so a 20-minute note reports 1200. The hub carries the same two numbers in `plugin/protocol.py` (`NOTE_MAX_BYTES`, `NOTE_DURATION_MAX`), which `plugin/notes_ingest.py` and `plugin/notes_pipeline.py` both read, so a note the firmware accepted cannot be refused, quarantined or clamped at ingest; the Recording screen's cap line reads `OF 24:00` instead of clamping to `99:59`. The endpoint spools the request to `notes/.staging/` and parses an `mmap` of it with zero-copy part views, so a multi-gigabyte note no longer needs the body held two or three times in RAM, and an upload that does not fit the disk answers 507 (retryable) before a byte reaches an entry. ## Unreleased

- **A note whose body goes quiet on the wire is no longer thrown away and re-sent from byte 0.** `cfg.timeout_ms` (20 s) is applied by `esp_transport` to *every* write's `select()`, so a quiet stretch in the middle of a body aborts the POST and discards everything already streamed, and the 10 s backoff hashes and sends the whole recording again. Measured on the board with a per-step log (13 scripted 60 s recordings, 2.8 MB notes, the hub's own `ss` counters and a passive packet capture alongside): the body after a recording can be quiet for **66-81 s before its first bytes leave the chip**, and this is not a slow transfer — sampling every 64 KiB step shows the stall on the first write only (67,879 ms, 65,744 ms, 80,670 ms, 65,821 ms) and then 37-94 ms per step for the rest, i.e. 1.3-1.6 MB/s once it clears. The capture says where it is: the hub's SYN-ACK arrives with a 64 KiB window and is not answered for 80 s, the device transmits nothing on that flow for the same window, while its long-lived WebSocket flow keeps sending 6-byte pings throughout and the hub's receive queue stays at 0 with `retx=0`, so the hub was never the one not reading and no ACK was ever withheld. `Uploader::step` (`main/notes/notes_uploader.cpp`) now raises the clock to 120 s for the body only, right after `esp_http_client_open`, and leaves the 20 s connect-and-head clock above it untouched (an unreachable hub still fails as `cannot reach Hermes` in 20 s). 20 s cut two of five measured runs at the old value; a 60 s probe still cut two more (80,763 ms and 80,670 ms writes, `Poll timeout or error … timeout_ms=60000`, requeued) while a 65-77 s stall in the same build completed; 120 s is above every measured stall and still ends a body that has really stopped. Verified: `ctest` 8/8, and six scripted runs after the change each accepted on the first attempt with no `Poll timeout` and no resend — one 60 s, 2.8 MB note put its body out in 8.8 s (42 steps, 3.0 s for the first 900 KB on the wire, 300-370 KB/s at the hub, `HTTP 202 -> accepted` 16.6 s after `notes stop`). None of those six stalled, so the 120 s path itself was not exercised against a real stall; what is measured is that a clock shorter than the stall cuts the POST. The stall's own cause is per-boot and outside the notes code (the same build, hub, AP, channel and RSSI produced both), and is filed as a firmware measurement of its own.

- **An e-paper update no longer needs 5,000 bytes of free internal RAM, so a Wi-Fi transfer cannot blank it out.** `spi_common` logged `Failed to allocate priv TX buffer` twice during a 44 s, 2.1 MB note upload with `internal_min_free` at 68 B, and the transfer was unaffected: the failing allocation belongs to the panel, not to the notes. This chip's SPI cannot DMA out of PSRAM, where the driver keeps its 1-bit image, so each 5,000-byte panel write made the SPI driver ask internal RAM for a private buffer of the same size (measured: `dma_free` 1.9-4.9 KB, largest free block 1,856-4,864 bytes during and just after a transfer, against 8,192 at rest). The request failed with `ESP_ERR_NO_MEM` (the panel write's own return code, 257), the write was dropped without a check, and the panel kept the previous frame, so the `sent` screen of a finished upload could simply not appear. `EpdDisplay::write` (`main/port_display_epd.cpp`) now stages every write through one fixed 1 KiB internal DMA buffer allocated at `begin()`, so no panel update asks internal RAM for anything, and a write that still fails logs the byte it stopped at and requests a redraw with a full refresh rather than leaving a half-written frame. The other buffers stay in PSRAM (18.9 KB: framebuffer, image, snapshot), which is where the 128 KB recording ring and the 64 KB transfer buffer already live: measured on the board, both are `psram`, so the notes buffers are not what squeezes internal RAM. What does is the Wi-Fi socket path (internal free falls from 21 KB to 12 KB while a note streams) and it is still tight (`internal_min_free` 116-164 B, `dma_largest` 1,856 B), which is why the driver no longer asks. Verified on the board: the same 60 s, 2.8 MB note with `notes status` forcing a repaint every 1.5 s, which before the change produced three `spicommon_dma_setup_priv_buffer` failures with `dma_largest` under 5,000 in two runs, now sends 40+ panel writes through a transfer with `dma_largest` as low as 1,856, zero `spi_common` errors, zero `the panel took` lines, and `HTTP 202 -> accepted` on the first attempt in both runs.

- **A read of `recording.wav` that stops short is no longer taken for the end of the file.** `fread` answers 0 both at EOF and after a failed read, and the sending phase treated it as EOF: a 60 s, 2.8 MB note's first attempt put `head + 393,216` body bytes on a connection that had declared 2,861,484, the server sat waiting for the rest, the client waited out its 20 s answer timeout, the note was requeued, and the retry hashed and sent the whole file again (twice in a row on the board, 393,216 bytes and 2,490,368 bytes). The hash pass had the same hole: it would have signed a digest of a prefix. `notes::audio_read_short` (`main/notes/notes_uploader.hpp`) is now the rule both passes apply before anything else is done with the file: a read that does not reach the size `stat()` reported is a read failure, so the note is retried with the byte counts in the log line instead of a truncated body and a 20 s stall. The size is the test, not `ferror`: the board logged `sdmmc_cmd: allocate_dma_buf: not enough mem, err=0x101` then `diskio_sdmmc: sdmmc_read_blocks failed (0x101)` 60 ms before one of these stops, with the stream's error flag clear, because a failed read reaches `fread` as a short file. That allocation is the same internal DMA squeeze as the panel's: an SD read into a PSRAM buffer needs a temporary internal DMA buffer, and during a transfer the sdmmc host could not get even one 512-byte block. The guard turns that into a 10 s retry, which succeeded here (`HTTP 202 -> accepted` 15 s later), and the underlying squeeze is filed as its own measurement. New host case in `hg_epaper_notes_tests` over the rule alone (20 cases, `ctest` 8/8). Verified on the board: no truncated attempt in either verification run, both notes `HTTP 202 -> accepted` on the first attempt.

- **The card reads through its own internal DMA buffer, so a Wi-Fi upload can no longer run the internal heap out of the 512 bytes a sector read needs.** The note buffers are in PSRAM (the 128 KB capture ring, the 64 KB transfer buffer) and this chip cannot DMA out of PSRAM, so the sdmmc host took a temporary internal DMA buffer for every read and write and freed it again; during a 60 s, 2.8 MB upload that allocation failed with `sdmmc_cmd: allocate_dma_buf: not enough mem, err=0x101` after the transfer had already sent 196,608 of 2,875,564 bytes, the read came back to `fread` as a short file, and the note retried 10 s later (the short-read guard above). Attributed on the board rather than guessed: 40,707 B of internal RAM free five seconds after boot, 19,311 B once Wi-Fi and the Hermes socket are up, 10.5-12 KB while a note streams, and `dma_largest` 368-896 B at the moment the body flow started, against `dma_free` 4,119 B - the free total was there, the contiguous block was not. `sd_mount::ensure` (`main/notes/sd_mount.cpp`) now allocates one 2 KiB internal DMA buffer at mount and hands it to the host as `dma_aligned_buffer` with `unaligned_multi_block_rw_max_chunk_size` at 4 sectors: the card stages through memory it owns, both directions, and no read or write asks the heap for anything mid-transfer. The cost is a fixed 2 KiB, the largest chunk the driver's own allocation was actually getting during a transfer anyway (it halves from 8 KiB down to one sector), and it is why the throughput was re-measured instead of assumed: a 2.8 MB note's body moves at 350 KB/s and the hash pass at 580 KB/s, the same read rate as before the change (64 KB read 100-116 ms, write 38-100 ms per step). `internal_min_free` stays at 164 B, which is what the Wi-Fi connect path alone reaches before any note exists, so that number is not the thing this can fix and the card no longer fails on it. Verified on the board: the same 60 s note reproduced the failure on the first attempt without the change (196,608 of 2,875,564 bytes, `allocate_dma_buf` `0x101`) and uploaded on its first attempt with it, twice, `HTTP 202 -> accepted` in 16.0 s and 8.2 s of body time, with zero `allocate_dma_buf` and zero short reads in either run.

- **The ESP32-P4 boards link again, so a tag publishes itself.** `port_sdlog.cpp` is built for every board and calls `hgp::sd_mount::*`, but its implementation was listed with the e-paper note modules and so only compiled for `waveshare-epaper-154`: the CrowPanel P4 and the Waveshare P4 7B failed to link (`undefined reference to hgp::sd_mount::ensure(bool, std::string*)` and two others), which made `release.yml`'s `esp32p4` job fail and the release job skip, and v0.7.0 had to be published by hand. `main/CMakeLists.txt` now compiles `notes/sd_mount.cpp` for every target; a board with no card slot configures `sd.enabled = false` and the mount declines, as before. CI gains an `esp32p4` job that builds both P4 boards with `idf.py` in the ESP-IDF container, since PlatformIO has no P4 platform and no other workflow built them: the same link error now fails a pull request. Verified locally by building both boards with `espressif/idf:v6.1` before and after the change: the CrowPanel P4 failed to link at `port_sdlog.cpp:81` and now builds.

- **A note whose recording is gone stops retrying.** An e-paper note whose `notes/pending/<id>/` holds a committed `note.json` and no `recording.wav` (a recording interrupted after its metadata landed, a card that ran out of room) was handed to the uploader on every pass of the notes tick: the uploader refused it with `recording.wav is missing or empty`, the note stayed pending, and the console warned once per 30-40 ms for as long as the board was online, while `notes status` counted it pending and `0 B queued`. The queue now decides before the uploader opens the note, from the audio file's size alone (`hgp::notes::plan_upload`, whose 45-byte minimum the uploader shares): a note with no audio, or only a WAV header, moves to `failed/` once, terminal like a 4xx, and still goes away with `notes delete <id>` or `notes delete --failed`. A start the uploader refuses for any other reason (no memory, a file the card will not open) is now waited out on the contract's retry backoff instead of being retried every tick. Verified on the ESP32-S3 e-paper board: a pending note with no audio logged one `has no recording (0 B): moving it to failed/` and nothing in the 30 s after, and `notes status` read `pending 0 ... failed 1`; a new `hg_epaper_notes_tests` case covers the missing file, a bare 44-byte header, the move to `failed/`, and a 45-byte note that still uploads.

## 0.6.0

Hermes Gadget 0.6.0 gives the agent more to do with a gadget. It can play a sound file or a radio stream on the speaker (`gadget_play`), show lists, progress bars and QR codes, ask a question with up to six answers on the screen (`gadget_ask`), set the face's expression, and fill the idle screen with widgets such as a disk's fill level or the room temperature. Interpreter mode turns a gadget into a translator that two people pass back and forth. Messages and cron jobs sent to a gadget outside a turn are spoken, and `hermes gadget bot-chat` lets a gadget talk to Hermes Bot Mode. Profile switching works on a stock Hermes with `profile_mode: virtual`, and a board's diagnostics report comes over the network, with the reason for a hang or a restart. The M5Stack CoreS3 gains its camera, as a `camera.capture` action and a camera mode with a live view. Five experimental board profiles arrive: the M5Stack StopWatch, the M5Stack Cardputer ADV, the Seeed Studio SenseCAP Watcher W1-A, the Waveshare ESP32-S3-Touch-LCD-1.47 and the LCDWIKI ES3C28P. The Waveshare ESP32-P4-WIFI6-Touch-LCD-3.4C boots on esp-hosted 2.12, and its speaker pops less when it turns on and off. Details by area follow.

A message from Hermes then waits at most that long at the access point, well inside the 20 s heartbeat and its 60 s timeout. The screen lighting, a turn, or any other message from Hermes goes back to minimum modem sleep at once, and a turn or USB keeps the radio fully awake as before. The station asks the access point for a listen interval of 3 when it joins, and each switch is logged (`hg.wifi: power save: max modem`). A **Deep Wi-Fi sleep** settings item, or `set wifi_deep_sleep off`, keeps minimum modem sleep on battery as before, for an access point that drops or delays clients in deeper sleep; it is on by default and shows on ESP32 boards that read their battery. On a Waveshare AMOLED-2.06 under light use, discharges of the same firmware with the setting on and off reached 15% within 10 minutes of each other (6 h 22 min to 6 h 32 min), so no clear battery gain was measured on that board. [Hardware verification](docs/hardware-validation.md#waveshare-amoled-206-wi-fi-max-modem-sleep-report).

- The AMOLED-2.06 watch shows its battery percentage from a discharge curve measured on a real AMOLED-2.06, smoothed over a minute and never rising on battery, instead of the AXP2101 gauge. Over the measured discharge (8 h 14 min, light use, screen mostly dark) the gauge read 25% with 42% left, raised the 15% alert with 2 h 14 min left and reached 0% 11 minutes before shutdown; replayed through the curve, a full watch shows 100 right after unplugging, the percentage stays within 2 points of the time left on average, the 15% alert comes with 74 minutes left and 0% under two minutes before shutdown. A minute-long load dip can still read up to 8 points low until the charge catches up, and a heavier load reads a few points low. While charging it still shows the gauge, then 100 once charging is done: the cell reaches 4.18 V less than halfway through a charge, so voltage can't track it. Host tests replay the measured discharge; a build with the curve has not run on the watch yet. [Hardware](docs/hardware.md#esp32-s3-touch-amoled-206). Contributed by @BrOrlandi.
- Add the experimental `cardputer-adv` profile for M5Stack Cardputer ADV / Stamp-S3A: ST7789 display, ES8311 voice, USB provisioning, battery voltage and TCA8418 keyboard with a local text editor. OTA reception on this no-PSRAM profile limits queued firmware chunks to avoid exhausting internal RAM during flash writes and owns each completed receive payload across the admission wait. No SD card is required. Original Cardputer models are not covered.

- The Waveshare ESP32-P4-WIFI6-Touch-LCD-3.4C drives its speaker amplifier from the port, and every board whose port drives the amplifier now turns it on while the DAC is still muted and mutes before turning it off, with 20 ms to settle each way: the 3.4C, the AMOLED-1.75 and 1.75C, the AMOLED-2.06, the AMOLED-2.16, the LCD-1.85C V2 and the P4 7B. On the 3.4C only, the ES8311's DAC also ramps its volume on mute and unmute. Both aim at the pop when playback starts and stops. Built; not yet heard on any board, including the 3.4C. Contributed by @rahlquist.

- The Waveshare ESP32-P4-WIFI6-Touch-LCD-3.4C now boots on esp-hosted 2.12. Its mempool pre-allocates the SDIO and common TX buffers at `esp_hosted_init` — a constructor that runs before the main task exists — taking about 88 KB of the board's roughly 97 KB low heap and leaving too little for the 8.7 KB main-task stack, so startup panicked at `esp_startup_start_app` with nothing on screen. The 3.4C profile now turns `ESP_HOSTED_USE_MEMPOOL` off, so transport buffers allocate on demand as they did on esp-hosted 2.7. The same profile turns off REGDMA sleep-clock retention (the board never light-sleeps) and draws with CPU copies instead of DMA2D, the configuration it was run with. Run on a Waveshare ESP32-P4-WIFI6-Touch-LCD-3.4C rev 1.3 from an ESP-IDF 5.5.4 build of this change: it boots, the 800x800 DSI panel draws with CPU copies, both codecs and the touch start, and the device pairs and comes online. The ESP-IDF 6.1 image that releases use builds in CI but has not been booted on the board. Contributed by @rahlquist.

- A new **Animation** setting, on by default (`set animation off`): off, the edge ring's comet no longer runs while Hermes thinks, speaks, boots or connects, and the Updating screen stands still while a firmware update installs instead of blinking its spinner and dots. The timer arc and the update progress ring still show, because they carry information. Contributed by @rahlquist.

### Hermes plugin

- **Hermes can play audio on a gadget's speaker.** A new agent tool, `gadget_play`, plays a sound file from the Hermes computer or an `http(s)` URL (an audio file, a podcast episode, an internet radio stream), and stops it. The plugin decodes on the host, a chunk at a time, into the stream spoken replies use, so no firmware change is needed and a long stream is never held in memory. Playback starts after the current reply and ends at the end, after `play_max_minutes` (60), on `stop`, on CANCEL, when you talk to the gadget or when Hermes speaks. Formats other than PCM WAV, and all URLs, need `ffmpeg`. Local files are read only from Hermes's audio cache and the folders in the new `play_dirs` setting; URLs go through Hermes's URL policy, which refuses private and internal addresses, and `ffmpeg` is given no network or file access of its own and reads audio containers only, not playlists. A source that sends nothing playable within 15 seconds, or a stream that goes silent for 20, is given up on. See [Playing audio](docs/hermes-integration.md#playing-audio). The dev server's console gains `play <path>` and `stop`.
- The gateway stops the audio it is sending when the device starts a recording. The device had already stopped playing it; the rest of a reply was still sent and dropped.
- The agent can put more on a gadget's screen and ask a question there. `gadget_display` takes `items` (a list), `progress` (a bar from 0 to 100) and `qr` (text shown as a QR code), and a card sent again with the same `id` replaces the one on screen in place, so a progress bar moves. A new tool, `gadget_ask`, shows a question with 2 to 6 answers and returns the one the user picked, or that they cancelled. A gadget whose firmware predates this gets the same content as a plain card, and `gadget_ask` shows it the options as a numbered card and tells the agent to ask by voice. Hermes's own yes/no confirmations, and the rules for approving dangerous commands, are unchanged. `hermes-gadget devserver` has `show` and `choose` to try them. [Protocol: structured cards](docs/protocol.md#structured-cards), [choices](docs/protocol.md#choices).
- **Interpreter mode.** Two people who speak different languages pass a gadget back and forth, and it says and shows each thing in the other language. Start it with `hermes gadget interpret <device> <language> <language>` or by asking Hermes (the new `gadget_interpret` tool); leave with `off`, or by holding CANCEL on the gadget. What is said in the mode never reaches the Hermes agent: the plugin transcribes it, asks the model for the translation through Hermes's completion API for plugins, which carries no tools, and speaks the result, so the other person's words cannot trigger a tool or an approval, and nothing is added to a session or to memory. The speakers take turns and each recording is transcribed in the language whose turn it is; Hermes's speech-to-text cannot be asked to detect the language. A translation in a script the screen can't draw is still spoken, and the screen says so. While the mode is on the gadget shows no Hermes question and takes no answer to one, messages sent to it wait, and what it sends is marked, so a mode that ended meanwhile never turns a stranger's words into a Hermes turn; the mode outlives a gateway restart. It ends by itself after 30 minutes unused. Tested in the simulator and against a Hermes gateway with stand-in providers, not on a board. See [Interpreter mode](docs/using-gadget.md#interpreter-mode).

- A connected gadget's diagnostics report no longer needs a USB cable. `hermes gadget diag <name>` on the Hermes computer, or **Save diagnostics report** in the dashboard's Gadgets tab, asks the gadget through the gateway and saves the file `hermes-gadget diag` saves, plus the gateway's last 500 Gadget log lines, so a bug report has both sides of the same minutes. It works before pairing, too. The gateway sends a new `diag` message and the device answers with the report and its recent log (up to 16 KB); the protocol stays at version 1, and older firmware doesn't answer, so its report still comes over USB. Host and simulator tests only; not yet run on a board. [Save a board report](docs/troubleshooting.md#save-a-board-report).

- **Messages sent to a gadget outside a turn are spoken.** Hermes reads aloud only its replies to a voice turn, so a `send_message` or a cron delivery to `gadget:<device id>` reached a device with a speaker as text alone, and a speaker without a screen, such as an Echo Dot running LibreEcho, stayed silent. The adapter now also speaks such a message with Hermes's text-to-speech when the device speaks replies, with Markdown removed and, for cron output, Hermes's header, footer and truncation note. Messages play one at a time per device: each waits for audio already playing, and cron output that arrives during a turn waits for the turn; one that has waited two minutes stays text only. Before, a second clip cut off the first, which also happened between the files of one long clarify question. A caption sent with a voice file and the text of a clarify question are not spoken a second time. `/voice off` in the device's chat, or `speak_replies: false`, keeps them silent. Tried against Hermes v0.22.5 with Kokoro text-to-speech on two Echo Dot 2nd Gen speakers running LibreEcho and a Python gadget client; new adapter tests cover the spoken message, the cron wrapper, three messages in a row with no `audio.abort`, cron output during a turn, and the messages that stay silent. [Hermes integration](docs/hermes-integration.md#scheduled-delivery). First part of #304. Contributed by @NickJLange.
- **New and deleted profiles reach a connected gadget.** A profile created in Hermes reached a gadget's profile grid only at its next welcome, so it stayed missing until a reconnect or a gateway restart. The plugin now compares each switching device's offered profiles with Hermes's at every pairing check (every 2 s) and, when the list changed, sends the new `profiles` message ([protocol](docs/protocol.md#profiles)); thumbnails of new profiles follow. A list Hermes can't read sends nothing, so a failed read doesn't empty the devices' grids. Firmware that knows `profiles` replaces its list and redraws an open grid in place, keeping the page or moving to the last one; older firmware ignores it and gets the list at its next welcome. Tried on a Waveshare ESP32-S3-Touch-LCD-1.54 against Hermes v0.23.1 with the profile grid open: a profile made with `hermes profile create` was pushed one second later and appeared on the grid, and after `hermes profile delete` it left it the same way, with no reconnect; two Spotpear boards on the earlier firmware got the message and carried on. Contributed by Luiz Gustavo Saraiva (@luizgustavosaraiva).
- **A device that reconnects is welcomed at once.** After a device rebooted or changed networks, its old connection still looked open. The new connection closed the old one and waited for that close before sending the welcome, and the old connection's peer is gone, so the wait lasted until TCP gave up or the device's new network stack reset it. That took 0.07 to 3 s per reconnect on an AMOLED-1.75C over the tailnet, and in the meantime the pairing check sent `paired` and the dashboard before the welcome. The old connection now closes in the background. Contributed by Antonio Lourenco (@tozes).
- **Profile switching without the Hermes hook: `profile_mode: virtual`.** On Hermes versions with native session admission and without `validate_native_profile_route` (v0.22.5 to v0.23.1 and `main` today), every message to a picked profile failed with `profile_mismatch` (#232). With `platforms.gadget.extra.profile_mode: virtual`, a device talks to a picked profile in a chat of its own, `<device id>~<profile>`, and the plugin adds a `gateway.profile_routes` entry for that chat in the running gateway, so Hermes admits it as a routed chat. Each profile keeps its own sessions; routes of profiles deleted, parked or taken off the list are dropped at the next pairing check. Off by default. On Hermes v0.23.1 the gateway end-to-end switch passes in virtual mode and still fails with `profile_mismatch` without it; tried on a Waveshare ESP32-S3-Touch-LCD-1.54 switching between three profiles. [Hermes integration](docs/hermes-integration.md#running-against-a-profile-or-a-multiplexed-gateway). Contributed by Luiz Gustavo Saraiva (@luizgustavosaraiva).
- **`hermes gadget bot-chat <device> [profile]`: a gadget that talks to the other Bots.** Hermes Bot Mode gives a profile's canonical Bot Chat the `message_agent` tool, but a gadget's conversation is a session of its own, and moving the Bot Chat onto it took typing `/resume --all Bot Chat` on the device's USB console. The new command asks the gateway to switch the device to the profile and send that command from it, then waits until the profile's Bot Chat is on the device's chat. It checks first, and says what to change, when the profile has no Bot Chat, the gadget is not an admin of the gadget platform (`allow_admin_from`, which `/resume --all` needs) or the profile isn't offered. Tried on a Waveshare ESP32-S3-Touch-LCD-1.54 on Hermes v0.23.1: the command moved profile `nick`'s Bot Chat onto the gadget over the network; with the same `/resume` typed on the console, the gadget on profile `nina` asked two other Bots through `message_agent` and spoke their answers. [Hermes integration](docs/hermes-integration.md#a-gadget-that-talks-to-the-other-bots). Contributed by Luiz Gustavo Saraiva (@luizgustavosaraiva).
- **The model no longer takes the gadget's name as its own.** The per-device context now says the gadget's name is the device's, not the assistant's, so a profile answering through a gadget named after another profile keeps its own name. Contributed by Luiz Gustavo Saraiva (@luizgustavosaraiva).

### Upgrade and verification

Update the plugin first, with the commit-pinned command in the release notes, in every Hermes profile that has a copy (see [One profile per gadget](docs/hermes-integration.md#one-profile-per-gadget)). Then update devices with `hermes gadget update <device> --latest`, or use the [browser installer](https://adolanium.github.io/hermes-gadget-sdk/installer.html) for USB installation. Lists, progress bars, QR codes, questions, widgets, face expressions, interpreter mode and the diagnostics report over the network need both the new plugin and the new firmware. The new plugin still works with older firmware: a card that firmware can't draw arrives as a plain card, a question becomes a numbered card the user answers by voice, and a widget becomes a tile on the sessions list.

On Hermes versions with native session admission (v0.22.5 and later, including the current stable), a device that picks another profile is refused with `profile_mismatch` until NousResearch/hermes-agent#147690 lands. Set `profile_mode: virtual` to switch profiles without that change (see [#232](https://github.com/Adolanium/hermes-gadget-sdk/issues/232)).

Hardware ports remain experimental until a complete physical report is recorded for the exact revision; see [hardware capabilities and verification](docs/hardware-validation.md). Several entries above say "host tests only", "tested in the simulator" or "not yet run on a board": software tests and successful builds do not establish physical hardware verification.

### Firmware

- The screen shows Russian. The 5×7 font gains the Russian alphabet, U+0410..U+044F plus Ё and ё, in the same ASCII-art form as Latin-1; letters that look like Latin ones (А, В, Е, К, М, Н, О, Р, С, Т, Х and the lowercase а, е, о, р, с, у, х) reuse those glyphs. The device reports the display `charset` `latin1-cyrillic`, and the Hermes plugin keeps Russian for it. Other Cyrillic letters (і, ї, є, ђ and so on) still show as `?`. Firmware built with the Chinese font has the glyphs too but still reports `cjk`. An older plugin leaves `latin1-cyrillic` text unfolded: Russian shows there as well, but typographic quotes, dashes and emoji draw as `?`, so update the plugin before the firmware. Run on a Waveshare ESP32-S3-Touch-LCD-1.83 with Russian replies on screen.
- A recording survives a lost connection on boards with PSRAM. Before, the connection to Hermes dropping mid-recording ended the recording and lost it. Now the device keeps recording, with "Offline, still recording" on the Listening screen, and reconnects in the background. Once it is online again it sends the whole recording, and Hermes transcribes and answers as usual. A recording that ends while offline shows "Reconnecting to send..." and waits up to 45 s for the connection, then says "Couldn't send the recording". CANCEL discards it. The recording is kept in PSRAM (1 MB for 30 s at 16 kHz, 1.5 MB at 24 kHz, set aside at start-up only when about 1 MB of PSRAM stays free after it; start-up logs which way it went), and the upload sends from there, so a slow link now delays audio instead of dropping frames. A connection lost after the recording reached Hermes ends the turn as before. Boards without PSRAM are unchanged. `audio.start` gets optional `resent` and `age_ms` fields; the protocol stays at version 1. `diag` counts recordings held, sent again and dropped, and each buffered recording logs one line with its length, frames lost and the link's peak backlog. Host and simulator tests only; not yet run on a board. [The recording buffer](docs/architecture.md#the-recording-buffer). Contributed by @BrOrlandi.
- Lost connections explain themselves. Every loss is logged once as `connection closed: <reason> (<what the gadget was doing>)`, including timeouts such as `connect timeout` and `server silent`, and a lost network as `network down: ...`, whose Wi-Fi reason is kept as that close's reason. The reason now carries the signal strength and the cause when known. A send that gave up reads `disconnected: a 1286 B send in flight for 10000 ms; transport errno 11; rssi -74`, and a Wi-Fi loss reads `Wi-Fi lost (reason 200 beacon timeout, rssi -78)` instead of `Wi-Fi lost (reason 200)`. The server's close code also appears when it sends one. The end of a recording that lost frames also logs how many. `diag` adds `connection.closes`, the last five losses with when and during what, `connection.closes_total`, and `recordings.last`: the last recording's length and frames lost. Host tests only; not yet run on a board. [Troubleshooting](docs/troubleshooting.md#connection-and-pairing). Contributed by @BrOrlandi.
- The microphone's upload is lighter on boards that record at 24 kHz. Audio now goes in 40 ms frames at any rate, 960 samples at 24 kHz. Before, each 13 ms the codec delivered went as its own WebSocket message: 75 messages a second, each its own TLS record and send-queue slot. The 64-slot queue then held under a second of audio, so a link that stalled for longer lost frames: an AMOLED-2.06 behind a server on weak Wi-Fi lost half the frames of each recording. While a turn runs, the send task logs one `uplink:` line a second with the bytes sent, messages, longest send, queue peak, refusals, CPU clock and RSSI, so the next report says whether the device or the network fell behind. Host tests only; not yet run on a board. Contributed by @BrOrlandi.
- A short stall on the network no longer closes the connection to Hermes. A send that takes too long makes the WebSocket client close the whole connection, and the limit was 2 s: a Wi-Fi hiccup during a recording, the one time the device uploads 32-48 KB/s of audio, closed the connection and lost the recording, and an AMOLED-2.06 on a home LAN kept going offline in the middle of recordings. Sends and the client's reads now wait up to 10 s. A dead link is still found: a stalled send gives up after 10 s, and an idle connection still ends after three missed heartbeats (60 s by default). Host tests only; not yet run on a board. Contributed by @BrOrlandi.
- A reply is no longer lost when the screen goes dark before anyone reads it. Before, a reply that took a while showed for 20 s, the mascot came back, the screen timed out, and the press or touch that woke it showed the Ready screen; on a board without scroll buttons the reply could not be brought back. Now a reply counts as unread until a button press or touch lands on its text, and each wake from a dark screen shows it again from the top for 20 s. The Thinking screen also waits longer: once Hermes has sent `turn.start`, the device waits up to 30 minutes without a message (it was 3) for `turn.end`, with the screen lit, so a long task no longer drops to Ready and goes dark. A request Hermes never starts a turn for still gives up after 3 minutes. No setting changes, and a reply arriving on a dark screen wakes it as before. Host tests reproduce both cases; not yet run on a board. [Using the gadget](docs/using-gadget.md#device-settings-and-hardware-checks). Contributed by @BrOrlandi.
- A `wake_talk` setting and a **Talk from dark screen** settings item: on, a press of the TALK key (BOOT on the AMOLED-2.06) on a dark screen lights it and starts recording in the same press, holding to talk or starting a tap-mode recording, instead of only waking the screen. Touchscreen and PWR presses, a face-down gadget, the alarm, a question, a dark settings menu, and a gadget that can't talk to Hermes still only wake. Off by default, which keeps today's behaviour. [Using the gadget](docs/using-gadget.md#device-settings-and-hardware-checks). Tried on a Waveshare AMOLED-2.06.
- Pressing the TALK key twice quickly (BOOT on the AMOLED-2.06 and most other boards) goes back to Ready and asks Hermes for the default profile: a quick way out of another profile. The second press, within 0.4 s of the first, cancels the recording the first one started without sending it. It also stops a reply on its way and closes the profile list, the dashboard or a card. A single press or a hold still talks at once, with no added delay. Touchscreen taps, the press that only wakes a dark screen, the settings menu and questions keep their current behaviour. The **Double press home** settings item or `set double_home off` turns it off; it is on by default. [Using the gadget](docs/using-gadget.md#device-settings-and-hardware-checks). Tried on a Waveshare AMOLED-2.06.
- The relay TLS host test (`-DHG_TLS_TESTS=ON`) no longer fails about one run in a hundred. Its TLS server runs on a second thread and shares PSA Crypto with the client, and Mbed TLS 4.1 builds without locking by default, so the two handshakes raced: a failed handshake, or a heap corruption abort. The test build now turns on `MBEDTLS_THREADING_C` and `MBEDTLS_THREADING_PTHREAD`. In an Ubuntu 24.04 container, 1500 runs before the change failed 12 times and 1500 runs after it passed. Firmware builds are unchanged.
- `DsiDisplay` can drive an ST7123 panel over MIPI-DSI with Espressif's `esp_lcd_st7123` 1.0.2. `DsiController::St7123` selects it. Init commands are that component's defaults. No board selects it yet. P4-only. Built, not run on a board.
- `CodecAudio` can drive an ES8388 speaker through the ES8388 driver already in `esp_codec_dev`. `SpeakerCodec::Es8388` selects it. The I2C address is that component's 8-bit `ES8388_CODEC_DEFAULT_ADDR` (0x20), which the I2C driver shifts to 7-bit 0x10. The microphone stays an ES7210. No board selects the ES8388 yet. Built, not run on a board.
- `SpiDisplay` can drive an SPD2010 panel over QSPI with Espressif's `esp_lcd_spd2010` 2.0.0~1. The bus uses SPI mode 3. The driver refuses axis swap. The width it draws, including any x gap, must be a multiple of 4. The `esp32-s3-touch-lcd-146` profile selects it.
- New board profile `esp32-s3-touch-lcd-146`, experimental, for the Waveshare ESP32-S3-Touch-LCD-1.46. The 1.46B and the 1.46C share its wiki pin table. Round 412×412 SPD2010 over QSPI, SPD2010 touch at I2C 0x53, an I2S microphone and a PCM5101 speaker. 16 MB flash and 8 MB octal PSRAM. BOOT talks and a swipe down cancels. GPIO 0 is used as BOOT because the wiki names that button and does not print its GPIO. QSPI is 20 MHz in SPI mode 3. Color inversion, axis swap and both mirrors stay off. Touch reset and LCD reset are TCA9554 bits 0 and 1 at address 0x20. Backlight on GPIO 5 is active high. The microphone is an MSM261S4030H0R. The schematic ties L/R to 3V3, so the reader takes the right 32-bit slot and still treats each sample as 24 bits in that slot. Touch targets use 282 pixels per inch, the 412 pixel diameter divided by 1.46 inches. If touch INT is already low when the falling-edge handler is installed, the task reads once, which sends the SPD2010 its CPU-start command. A failed read is tried again on the next poll while the line stays low, because that read is what clears INT. An idle FT3168 sits high, so that board is unchanged. No amplifier-enable pin is listed. The QMI8658, PCF85063, TF card, battery header, volume knob and PWR button stay off. There is no 412×412 simulator profile. Built, not yet run on a board. [Hardware](docs/hardware.md#waveshare-esp32-s3-touch-lcd-146).
- New board profile `esp32-s3-korvo-2`, experimental, for the Espressif ESP32-S3-Korvo-2 with the LCD sub-board: a 2.4 inch 320×240 ILI9341 over SPI, GT911 or TT21100 touch, an ES8311 speaker and ES7210 microphones. 16 MB flash and 8 MB octal PSRAM. Hold the screen to talk and swipe down to cancel. GPIO 0 is the panel data line, so BOOT is not a button. Chip select, reset, backlight and the LCD/touch enable are TCA9554 outputs. The panel is BGR, both axes are mirrored, and color inversion stays off. The stock ILI9341 initialization is used. Touch mirrors X for both controllers. ## 0.4.0

Hermes Gadget 0.4.0 gives each Hermes profile its own face on the device, adds countdown timers that Hermes sets through device actions, face-down sleep on boards with a motion sensor, and a resting clock kept by network time and the board's RTC. It adds two experimental boards, the ESP32-2432S028 "Cheap Yellow Display" (the first classic ESP32 profile, drawn in bands without PSRAM) and the Waveshare ESP32-P4-WIFI6-Touch-LCD-3.4C. Profile switching no longer writes into other Hermes profiles and keeps the default profile's verdict even under a static route, and a switching device's dashboard lists the offered profiles' sessions, in order. Details by area follow.

### Hardware and setup

- Experimental board support for the ESP32-2432S028 "Cheap Yellow Display" (`esp32-2432s028-cyd`), the revision with two USB ports: a classic ESP32-WROOM-32 with 4 MB flash and no PSRAM, a 320×240 ST7789 on SPI2 and BOOT as the only key. The original micro-USB-only CYD has an ILI9341 panel and is not supported by this profile. It is the first classic-ESP32 profile, so the RGB, i80-parallel, MIPI-DSI and audio-codec drivers are compiled out and the panel uses the existing SPI `SpiDisplay` path and ESP-IDF's built-in ST7789 driver. No PSRAM means the full 150 KB framebuffer does not fit in internal RAM, so the port holds a 120-row band (75 KB) instead, reserved in an early constructor before the heap fragments, and flushes through a four-row bounce buffer; the UI renders each changed band once per window, so the screen is drawn in full without a whole-panel buffer. The board's XPT2046 touchscreen and microSD are not brought up. The SC8002B amplifier behind the speaker header is fed by the chip's own DAC on GPIO26 and plays three boot beeps, so the amplifier and a speaker can be checked before replies are routed there; those still come out as text. The 4-pin header also takes a PDM MEMS microphone (clock on GPIO22, data on GPIO27, SELECT tied to ground), read through the classic ESP32's PDM-to-PCM converter on I2S0 — the same path the P4 profile uses; the stock board has no microphone fitted, and an I²S microphone (three signal lines) cannot be used on those pins. A display that holds only a band of rows doesn't offer `display.image` in its hello, so Hermes shows its unsupported-image notice instead of sending an image the board would drop. Experimental: the firmware builds, but it has not been run on a board and the physical checklist is not completed. The pin map follows the community ESP32-Cheap-Yellow-Display reference. Contributed by Tony Tran (@thanhtantran).
- Experimental support for the Waveshare ESP32-P4-WIFI6-Touch-LCD-3.4C (SKU 31523): round 800×800 MIPI-DSI JD9365 panel, GT911 touch, ES8311 speaker with ES7210 microphones, and Wi-Fi 6 through the ESP32-C6 companion over 4-bit SDIO. The DSI driver now selects its panel controller (EK79007 or JD9365) from the board config instead of hardcoding the CrowPanel's EK79007. The profile builds with `idf.py`, since PlatformIO has no ESP32-P4 target (CI builds it; releases don't include it yet), and needs `CONFIG_ESP_CONSOLE_USB_SERIAL_JTAG` for the console, plus an esp_hosted slave image flashed to the C6 over its own UART header. Experimental: owner-confirmed display, C6-hosted Wi-Fi, pairing, reconnect after restart, factory reset and a one-hour run; touch, microphone, speaker and the full checklist are not verified. Contributed by Richard Ahlquist (@rahlquist).

### Firmware

- Each Hermes profile can have its own face. The plugin sends the face of the profile that answers a device: the profile's `gadget-face.bin`, made with `hermes-gadget face --out gadget-face.bin`, or else its Hermes avatar (`assets/avatar.*`) made into a still face when Pillow is installed. Without either, the device shows the mascot. A profile a device switched to shows its face once the default profile trusts the device; a profile a gadget route sends it to shows its face once that profile accepts the device. The device keeps the face in memory through reconnects, and shows the mascot after a profile switch until the new face arrives. `platforms.gadget.extra.profile_faces: false` turns faces off. Firmware without the feature keeps the mascot; the protocol adds `caps.faces`, `hello.face` and a `face` message, and stays at version 1. Contributed by @mforce.
- Face-down sleep, off by default, on boards with a motion sensor and a backlit display (first the Waveshare ESP32-S3-Touch-AMOLED-1.75): turn it on with the new **Face-down sleep** settings item or `set face_down_sleep on`. After about a second face down the screen goes dark, listening is cancelled and Hermes goes quiet: a reply being spoken stops and speech that arrives face down is dropped, while the turn carries on. The reply's text shows from the top when the gadget is turned back over. A ringing timer alarm goes quiet and stays quiet after the turn-over; a timer that ends face down still rings, with the screen dark. Adds a QMI8658 accelerometer driver (`firmware/drivers/qmi8658.cpp`). The simulator's `sim-466x466-round` board has the sensor (Developer tools **Face down**, script command `facedown on|off`); rebuild its native library for ABI 7. Contributed by @momoshamiko.
- Resting clock, off by default, on every board with a display: after the `clock` setting's seconds of rest on an online, paired Ready screen, the screen shows the time and the date, with the profile's face or the mascot, at 70 percent of the brightness setting, shifting a little each minute; a quick tap brings Ready back, and anything on screen keeps the clock away — speech or a reply, a card or a picture shown until dismissed, a question, a notice, a running timer, the alarm, the low-battery warning or the settings menu. Set it with the **Clock face** item (Off, 30 s, 1, 2 or 5 min) or `set clock` (0 or 5..3600 seconds), with `set time_format 12h` for 12-hour time and, on the ESP32 port, `set timezone` (POSIX TZ string, default `UTC0`). Network time (SNTP, `pool.ntp.org`) is fetched only while the clock is on; boards with a PCF85063 (AMOLED-1.75, 2.06, 2.16) keep UTC across resets and are set from each sync. A `screen.brightness` action no longer lights a dimmed or timed-out screen: the new level applies when it wakes. The simulator's `time` script command pins the clock's time; rebuild its native library for ABI 8. Contributed by @momoshamiko.
- Audio written right after a speaker stream starts is no longer thrown away on boards whose speaker task empties its queue after an abort: I2S speakers, and codec speakers without `codec.speaker_pa`. `begin()` aborts the stream before it, and the task emptied the queue on its next pass, so audio queued in between, such as a short tone written at once, could go with it. When `begin()` replaces a stream it now waits for that reset, at most 6 ticks (about 60 ms), as the P4 speaker also waits in `begin()`, so `write()` stays non-blocking, and an idle speaker starts at once. The task drops what it received while a reset was pending, and a codec cuts a stream's silent tail short when the next stream waits. A codec stream that closes with nothing played also no longer leaves `busy()` true until the next stream, which kept the screen from sleeping. Contributed by @momoshamiko.
- Timers: Hermes can start, check and cancel one countdown timer with the device actions `timer.start`, `timer.status` and `timer.cancel`, on any board with a display or a speaker. The time left shows on every screen: an arc around the edge of round screens, a line under the top bar of rectangular ones, and "Timer 6:18" on the Ready screen. At zero the screen shows TIMER DONE with the timer's name, and a board with a speaker beeps for a minute. A press, a tap or swipe, or `timer.cancel` stops the alarm. Contributed by @momoshamiko.

### Hermes plugin

- Profile switching no longer writes into other Hermes profiles. The plugin used to approve a switching device in each profile's pairing store itself; now each profile approves it through its own pairing flow the first time the device talks to it, and the device shows the command to run (`hermes -p <profile> pairing approve gadget <code>`) instead of waiting for a reply. The default profile's verdict comes from the adapter's own sender check. A device that has switched but that a static route now sends elsewhere is refused, so another profile's approval never stands in for the default one (found by @mforce). Asked for in the Hermes plugin catalog review ([NousResearch/hermes-agent#142936](https://github.com/NousResearch/hermes-agent/pull/142936)).
- Validate device-selected profiles during Hermes native session admission and durable replay, retaining Default-owner trust, offered-profile policy and owner binding. Requires the matching Hermes `validate_native_profile_route` hook; without it, a secondary profile can be selected but ordinary messages fail with `profile_mismatch`. Contributed by @bricelb.
- With profile switching on, a gadget that can switch profiles also lists on its dashboard the sessions of the other profiles it may switch to, where the gadget plugin is enabled, so a device switched to another profile sees its sessions there. Hermes loads a copy of the plugin per profile, and each copy records only its own profile's sessions; the default profile's adapter now also reads those of the offered profiles. With switching off, and on devices that cannot switch or that a profile route sends somewhere, the dashboard is as before. [User guide](docs/using-gadget.md#watch-hermes-sessions-on-the-dashboard). Contributed by @mforce.
- A switching gadget's dashboard no longer shows a profile that has just left the offer, or misses one just added, when two updates overlap, and a gadget that cannot switch no longer stops the other profiles' changes reaching it. Reading the profile list never makes a connecting gadget wait for a slow one. A dashboard held while the screen is dark is dropped if a newer one goes out first, and is never sent to a device that is unpaired or reconnects without dashboard support. Contributed by @mforce.

### Firmware

- The `language` setting takes `auto`: the device shows its own text in the language Hermes names in `welcome`, matched by id and then by primary subtag (`es-mx` as `es`), and in English when Hermes names none or one the firmware lacks. English stays the default. The settings item steps through the languages and then **Automatic, as Hermes**, `screen.language` accepts `auto`, and `status` reports `language` and `language_auto`. Contributed by Alberto Espinosa (@AlbertoEJ).
- The font draws Latin-1 (U+00A0 to U+00FF): accented letters, ñ, ç, ¿, ¡, °, « » and the rest, in the same 5x7 cell. An accented capital is its letter on five rows under the accent; a small letter sits on four rows with a blank row under the accent, so ó and Ó differ. Text is now read as UTF-8 everywhere it is drawn, measured, wrapped or cut, so a letter is one column however many bytes it takes; a code point outside the font draws as `?`. Translations show as written ("Información", "¿Lo oíste?"), and the device reports `charset: "latin1"` in `hello`, so the plugin stops folding accents for it. Tests check every Latin-1 glyph is its own, UTF-8 decoding survives malformed input, and wrapping and cuts never split a letter. Contributed by Alberto Espinosa (@AlbertoEJ).
- Spoken replies can travel as Opus: devices that decode it list `"opus"` in `caps.speaker.formats`, and the plugin then sends one Opus packet per 40 ms frame at 24 kbps (`opus_bitrate`, 0 for PCM16), about a tenth of PCM16 at 16 kHz. ESP32 boards with a speaker decode it with Xiph's libopus (the `78/esp-opus` component); the plugin encodes through the host's libopus and keeps PCM16 without it. Older firmware and servers keep PCM16. On one home Wi-Fi link, a board that logged 60 to 113 speaker underruns per reply with PCM16 logged none with Opus. The main task's stack grows from 8 to 20 KB for libopus's decoder scratch. Contributed by Luiz Gustavo Saraiva (@luizgustavosaraiva).
- The opt-in voltage estimate (`set battery_estimate liion`) follows a typical single-cell Li-ion resting-voltage curve instead of a straight 3.3–4.2 V line, which read up to about 20 points high in the middle of the discharge (3770 mV is now 30%, not 52%; 3840 mV is 50%, not 60%). A voltage reads high on a charger, so while the board reports charging or external power the title bar shows the battery icon with a charging bolt and no number, whatever the indicator style, and the Power page marks the value as high on a charger. The charging icon now draws a bolt over a dim green fill, so it reads at any level. Gauge percentages (AXP2101) are unchanged. Contributed by Luiz Gustavo Saraiva (@luizgustavosaraiva).
- The Waveshare LCD-1.54 and the Spotpear muma save battery like the AMOLED-1.75C: the CPU drops to 80 MHz when idle, and while the screen is dark on battery the chip takes light sleep between Wi-Fi beacons. Light sleep now keeps a battery latch's enable pin, an SPI panel's control lines and a separate touch bus at their level; before, a latch-powered board would cut its own supply on its first light sleep. Contributed by Luiz Gustavo Saraiva (@luizgustavosaraiva).
- Holding the title bar opens settings on the AMOLED-1.8 again. Its touch controller reports glass rows, and the UI starts 8 rows down (`touch.offset_y`), so touches on the top rows of the glass came out at negative rows (`y = -7` on a V2 board) and missed the title strip: holding the title started a recording instead. Rows above the UI now count as its first row. The AMOLED-2.06 uses the same offset and gets the same fix; it was not checked on hardware. Contributed by Alberto Espinosa (@AlbertoEJ).
- The device's own text can be shown in another language: Spanish for now, and more by adding a translation file. The strings moved into one catalogue (`hg/i18n.hpp`) with a table per language that falls back to English for anything it leaves out, and placeholders so a translation can order the words its own way. A `language` setting (`en` by default, or `es`) is chosen from a new **Language** item in device settings, with `set language` on the console, or by asking Hermes, through a new `screen.language` device action. Translations are written with their accents and shown without them until the font draws them. Tests check each translation is complete, keeps the English placeholders, and fits on one line wherever the English does on every supported screen size. Replies from Hermes are not affected. Contributed by Alberto Espinosa (@AlbertoEJ).
- Frame timing for renderer work: the console's `perf` command reports drawing, flush and whole-update times (min, average, p50, p95, max), bands sent per update, updates over a frame budget, and the time from a button or touch to the update that shows it. `perf bench` draws three fixed workloads (scrolling a long reply, the talking mascot, full repaints) so a change can be measured before and after; `examples/scripts/perf.txt` runs it in the simulator. Off by default (`perf on`, or `CONFIG_HG_FRAME_STATS` from boot); while off, the renderer never reads the clock. The HAL's `System` gains `now_us()`. See the development guide.
- Rejoining Wi-Fi skips the channel scan. After each good join the device records the access point's BSSID and channel (NVS key `wifi_fast`). At boot and after the link drops, the first attempt aims straight at it. If that attempt fails, the device joins normally at once, and the failure doesn't count against the network or lengthen the battery backoff. DHCP asks for the last address first (`CONFIG_LWIP_DHCP_RESTORE_LAST_IP`), and `CONFIG_HG_WIFI_REUSE_IP` (off by default) reuses the last lease as a static address for routers that reserve it. Reconnect times were not measured on hardware. Prompted by @dcentgeo's ESP32-S3 watch build.
- The device tells Hermes when its screen goes dark and lights up (`display_sleeping` in `hello` and in `state`), so the plugin can hold back screen updates; see the Hermes plugin entry.
- A connection that the server, a reverse proxy or a tunnel drops no longer leaves the device wedged until a reset. Firmware 0.2.0 waited on the WebSocket client from the app task, so a dropped connection could stop that task for good: the event queue filled (`event queue full; dropping event 6`), console commands were not applied, and the device never reconnected. On `main`, sends and closes already ran on their own task (the Wi-Fi-loss fix below). The last wait with no limit, handing a closed client to that task, now gives up after 1 s. If the send task spends more than a minute on one message or close, the device logs `the WebSocket send task is stuck; restarting` and restarts. Reported by @Taxgab.
- `wss://` servers behind Cloudflare, including quick tunnels (`*.trycloudflare.com`), pass certificate validation. Cloudflare sends GTS Root R4 cross-signed by GlobalSign Root CA, and the certificate bundle looked up only the issuer of the last certificate sent: GlobalSign Root CA is no longer in ESP-IDF's bundle, so the handshake failed with `No matching trusted root certificate found` although GTS Root R4 is bundled. Every board now enables ESP-IDF's cross-signed verification (`CONFIG_MBEDTLS_CERTIFICATE_BUNDLE_CROSS_SIGNED_VERIFY`), which trusts a chain at the first certificate a bundled root issued, for about 700 bytes of heap. The remote access guide explains how to check a server's chain. Reported by @Taxgab.
- Add an explicitly enabled, display-only single-cell Li-ion voltage estimate (`set battery_estimate liion`) for voltage-only power drivers, including LCD-1.54. Confirm a compatible fitted battery before enabling it; charging affects accuracy. Existing native percentages, raw telemetry, alarms, and default-off indicator settings are unchanged. The simulator now accepts full power readings through Python, scripted `power` JSON, and compact desktop controls; rebuild its native library for ABI 6. Contributed by Pablo Musaber (@PabloMusaber).
- AMOLED boards whose screen window is shorter than the glass (the 1.8 and the 2.06) blank the rows above and below it at start-up. Nothing else writes them, and the panel's memory starts out as noise: on the 2.06 it showed as green strips along the top and bottom edges. Seen and fixed on the 2.06; the 1.8 uses the same layout and was not checked on hardware. If clearing fails or times out, the gadget runs without the display so drawing cannot overwrite a pending DMA transfer. Contributed by Geo (@Geofresh).
- When a spoken reply finishes, the serial log reports how often the speaker ran out of audio mid-reply and for how long (`playback ended: N underruns, X ms in total, longest Y ms`), on every board with a speaker. Choppy replies on a weak link can now be measured instead of described. Contributed by Antonio Lourenco (@tozes).
- A recording no longer gets stuck on "Sending..." on a slow uplink. Microphone audio could fill the WebSocket send queue, so the message that ends the recording was refused and Hermes waited for the rest; the device showed "Thinking" for three minutes. The last slots of the queue are now kept for control messages, so audio is what gets dropped, and the serial log says how many frames of the recording weren't sent. If the end still can't be sent, the device shows "Couldn't send the recording" at once. Contributed by Antonio Lourenco (@tozes).
- The AMOLED-1.75C light-sleeps while dozing: on battery, with the screen off, idle and connected (or waiting between Wi-Fi attempts). The speaker codec and its I2S channel close while dozing, the speaker task waits instead of polling, and touch is checked every 50 ms. On USB it never light-sleeps, so the serial console, flashing and JTAG keep working. Waking the screen or plugging in retries Wi-Fi at once. Contributed by Antonio Lourenco (@tozes).
- The device keeps up to five Wi-Fi networks and joins whichever is in range. When the link drops it retries the same network once, then scans and picks the network that last worked if it is there, else the strongest saved one. A network that keeps failing is passed over while another is in range. The console's `wifi list`, `wifi add`, `wifi join` and `wifi forget` manage the list, and `wifi add` saves a network without joining it. `set wifi_ssid`, the web installer and phone setup now save their network first and keep the others. The first network is also kept under the old keys, so older firmware still finds it. Contributed by Antonio Lourenco (@tozes).
- An experimental Bluetooth LE link for a phone companion app. A paired phone sends the same commands as the USB console and gets the same replies, so an app can set up Wi-Fi, change settings and read the device's status. Pairing opens for two minutes from a new **Phone app** item in device settings or the `phone pair` command, and the phone types the six-digit code the screen shows. The link is off on every board: a board turns it on with a `BoardConfig` flag and NimBLE in its `sdkconfig.defaults` once it passes the Bluetooth checks in the hardware verification guide, so released images don't grow until then. Contributed by Antonio Lourenco (@tozes).
- Wi-Fi modem sleep is on only while the board runs on its battery and no turn is under way. Plugged in, on a board that cannot tell, or during a turn (from pressing TALK, through the wait while Hermes works, until the reply has finished playing), the radio stays awake, so reply audio no longer arrives in bursts that overflow the speaker buffer and crackle. Reported and diagnosed by @burndown; keeping the radio awake through a turn on battery contributed by Antonio Lourenco (@tozes).
- The I2S microphone driver (breadboard and custom-pin boards) keeps the samples of a read that times out part way. On ESP-IDF 6.0.1 nearly every read returned `ESP_ERR_TIMEOUT` with one DMA buffer filled, the driver dropped it, and a held TALK sent 0 bytes of audio, so Hermes never replied. Contributed by @burndown.
- A dark screen stays dark while Wi-Fi or the connection to Hermes drops and reconnects; it used to light up and, without a screen timeout, stay on until someone turned it off. Contributed by Antonio Lourenco (@tozes).
- The AMOLED-1.75C shows its battery percentage from a discharge curve measured on its 500 mAh cell, smoothed over a minute and never rising on battery, instead of the AXP2101 gauge, which read up to 14 points low on this cell, or the linear voltage estimate used when the gauge is invalid, which was off by up to 13 points. While charging it follows a charge curve measured on the same cell, never falling, and shows 100 once charging is done; `diag` reports the PMIC's charge current limit. Builds on the voltage fallback for invalid gauge readings. Contributed by Antonio Lourenco (@tozes).
- Boards with a separate ES7210 microphone ADC (the AMOLED-1.75 and 1.75C, the 1.85C V2 and the LCD-1.54) power it down between recordings instead of running and reading it continuously, which saves battery. Recording starts by draining the audio the I2S channel kept while the ADC was off and dropping 20 ms while it settles. Boards whose microphone shares the speaker's codec keep reading continuously. Contributed by Antonio Lourenco (@tozes).
- Boards that report a battery percentage show it at the top of the screen: a battery icon and the percentage in the title bar, or centred at the top edge of round displays, green while charging and red at 10 percent or less without USB. Selecting **Battery and power** in device settings cycles it through icon only, percentage only, both and off, when the board has a percentage to show; the console takes `set battery_display icon|percentage|both|off`. It is off by default and the choice survives restarts. Contributed by Antonio Lourenco (@tozes).
- On battery, Wi-Fi retries back off from 3 s to 30 s, like the Hermes reconnect, instead of trying every 3 s, so a long stretch without coverage costs little. Plugged in, they stay at every 3 s. Contributed by Antonio Lourenco (@tozes).
- AMOLED boards (the 1.75, 1.75C and 1.8) draw the background true black instead of near black, so those pixels stay off and draw no power. Backlit LCDs keep the near-black background. Display drivers opt in with `DisplayInfo::emissive`. Contributed by Antonio Lourenco (@tozes).
- Battery life on the AMOLED-1.75C: the speaker amplifier is powered only while sound plays, and the CPU scales down to 80 MHz when idle instead of running at 240 MHz. AMOLED panels also switch their output off during screen sleep, not only their brightness. Contributed by Antonio Lourenco (@tozes).
- The AMOLED-1.75C's PWR key puts the screen to sleep and wakes it with a short press. Only the AXP2101 sees this key, so the firmware enables the PMIC's short-press interrupt and polls it every 100 ms; holding PWR keeps the PMIC's own power behavior. Contributed by Antonio Lourenco (@tozes).
- The `diag` report's I2C scan no longer gives up at the first probe that times out. On the AMOLED-1.75C it reported `bus stuck` after `0x18` while the AXP2101 at `0x34` was answering battery reads. A probe waited 10 ms, a single tick at the firmware's 100 Hz tick rate, which can run out before the transfer ends; a probe also times out while touch, codec or battery reads hold the bus. Each address now gets up to three 50 ms tries. An address that never answers is listed as `timeout at 0x19` and the scan goes on; only four in a row end it, as `bus stuck at` the first of them. `hermes-gadget diag` now separates the entries with commas. The scan is host-tested.
- Boards that play through an ES8311 or AW88298 codec run their audio at 24 kHz instead of 16 kHz and buffer 192 KB of speaker audio in PSRAM instead of 48 KB, so they absorb a longer Wi-Fi burst before dropping audio. They play silence into the I2S DMA buffer before muting, so the end of a reply is no longer cut off. Contributed by 0xdfi.
- A weak or lost Wi-Fi link no longer freezes the device until a hard reset. Closing the WebSocket used esp_websocket_client_close(), which sends its close frame with no time limit and blocked the app task, and with it the screen, touch and Wi-Fi retries, on a dead link. Sends now run on their own task with a 2 s limit, so a slow link no longer stalls the screen either, and a lost connection is noticed even when its event can't be queued. Contributed by Antonio Lourenco (@tozes).
- A console command that times out no longer leaves the app task writing its reply into freed memory. The request slot is shared by both tasks and freed by whichever finishes last, so a late reply is dropped instead of corrupting the stack. The slot is host-tested.
- The device refuses an over-the-air image built for another board, by reading the `HGBOARD=` tag as the image streams in, so a wrong image can no longer reach Wi-Fi and Hermes and pass the rollback check. The plugin's own check stays as the first line.
- Builds from `main` with that board check no longer refuse every over-the-air update with "the image is for , not this board". The check's search text put a nameless copy of the `HGBOARD=` tag in every image, ahead of the real one, and the device stopped at it. Images now carry the tag once, and the device, the plugin and the release packager skip a nameless tag in images built before this fix. Contributed by Antonio Lourenco (@tozes).
- A setting that cannot be saved is reported: `set` answers `@error could not save <key>`, a device key that cannot be saved is logged as an error, and a key longer than NVS allows is refused instead of silently cut.
- The CrowPanel 2.1 no longer drives GPIO 0, its BOOT key, high, so pressing BOOT while it runs no longer shorts a driven output to ground. The RGB panel setup left the display-enable pin at zero, which claimed GPIO 0 and made the ST7701 driver turn the screen on through that pin. The panel now has no enable pin, and the driver sends the display-on command over the 3-wire link instead. Not yet checked on a board.
- Display transfers no longer race their own DMA: the AMOLED-1.75/1.75C/1.8 and T-Display-S3 drivers now use the same band-by-band flush as the SPI panels, so a late or failed transfer pauses or stops drawing instead of refilling a buffer the DMA is still reading. The CrowPanel RGB path reports a failed flush or backlight change once instead of rebooting, and a display that fails to start leaves the gadget running without a screen (USB console and Wi-Fi still work) instead of rebooting in a loop. A touch task that cannot start is reported as a failed input.

### Linux

- The Raspberry Pi installer installs the release's pinned Python dependencies from a hash-checked lock file shipped in the package, wheels only, so a Pi runs exactly what CI tested instead of whatever PyPI serves that day. The release workflow runs the container install test before publishing.
- The Raspberry Pi installer checks that a new release answers on its control socket before calling the update done, and goes back to the previous release when it does not, matching the firmware's rollback. `sudo hermes-gadget-device rollback` swaps the current and previous releases by hand. A dependency installation that fails is removed instead of blocking the next attempt, the newest three releases are kept, and a release that keeps crashing at startup stops being restarted after five tries.

### Hermes plugin

- Switch which Hermes profile answers a gadget: on a touchscreen, tap the name under the mascot and pick a profile from the list; elsewhere, use **Hermes profile** in settings. Pair once, on the default profile: the plugin approves the device in each profile the first time it switches there, and revoking it on the default profile sends it back to default. Off unless the default profile's gadget `extra` sets `profiles`: `[work, home]` offers those and the default profile, `all` every profile a multiplexed gateway serves. Other profiles' configs cannot turn it on. Enable the gadget platform in the default profile only. A gadget with a `gateway.profile_routes` entry keeps its route and is not offered switching. Protocol: `hello.caps.profiles`, `welcome.profile` and `welcome.profiles`, `profile.select` and `profile` (additive; `proto` stays 1).
- `welcome` names a `language` for devices left on `auto`: the plugin's `language` setting, else Hermes's own (`agent.i18n.get_language`, so `HERMES_LANGUAGE` and `display.language` per profile). If it can't be read, `welcome` names none and the device stays in English. `hermes-gadget devserver --language es` does the same for the simulator. Contributed by Alberto Espinosa (@AlbertoEJ).
- Devices that report `charset: "latin1"` keep their accents: replies, notices, questions, cards and the dashboard are folded to ASCII and Latin-1 instead of to ASCII (`textfmt.fold_latin1`). Other scripts still fold to the nearest letter or drop, and emoji drop. Devices reporting `"ascii"` are unchanged. Contributed by Alberto Espinosa (@AlbertoEJ).
- A cancel that arrives when no turn is running no longer sends `/stop` to Hermes. Before, the stray `/stop` reached Hermes as a message of its own.
- A profile routed to the default profile's gadgets (`gateway.profile_routes`) has the gadget tools again. Hermes imports the plugin once per profile scope, so each copy kept its own empty adapter registry, the tools' availability check failed, and the agent reported `gadget_action` as missing. The registry is now one per process. The integration guide describes routing each gadget to its own profile. Contributed by Luiz Gustavo Saraiva (@luizgustavosaraiva).
- A dashboard on the device lists the Hermes agent's sessions, from every platform, as idle, busy or waiting for an approval, plus status tiles set on the host with `hermes gadget tile set nas up --state ok` (for homelab services and the like; `--ttl` makes a tile expire). Tap CANCEL on the idle screen, or swipe down on a touchscreen, to open it. Session state comes from Hermes's plugin hooks. The plugin sends a new `dashboard` message only when something on it changes, and while the screen is dark it keeps only the latest for when the screen lights up. `dashboard: false` turns it off. New firmware is needed to draw it. Checked in the simulator only, not on hardware. Prompted by @dcentgeo's ESP32-S3 watch build. [User guide](docs/using-gadget.md#watch-hermes-sessions-on-the-dashboard), [protocol](docs/protocol.md#dashboard).
- An approval whose time ran out while its device was offline no longer comes back on reconnect. Approval cards carry Hermes's approval timeout (`approvals.timeout`, 300 s by default) as their time limit, and the adapter drops a card once that time has passed.
- While a gadget's screen is dark, cards, images and status phrases wait. When it lights up, only the latest card or image and the latest status phrase are sent, and a card keeps only the time it has left. Questions, approvals, replies, audio and notices still go out at once. `gadget_display` says when its card is waiting, and `gadget_devices` reports `display_sleeping`. Firmware that doesn't report its screen is never held back. [Protocol: screen sleep](docs/protocol.md#screen-sleep).
- A command approval on a device shows the command exactly as it will run. The card used to pass through the reply formatter, which strips Markdown: `ls <think>; curl … | sh ;</think>` showed as `ls`, and TALK approved the whole command. A command that doesn't fit one line of the device's screen as-is (longer, multi-line, with a tab, double space or non-ASCII character) now shows "Can't show this command": CANCEL denies it and TALK does nothing, so it is approved on the host. Reported in the Hermes plugin catalog review.
- A device that loses its pairing loses its open questions, and an answer from an unpaired session is ignored. A revoked device could still answer a question queued before the revocation.
- The plugin README shows how to bind `host` to one interface and serve `wss://` with `tls_cert` and `tls_key`.
- The plugin declares the Hermes it needs (`requires_hermes: ">=0.21.6"`, the first release with the commit CI tests against), and has its own README: what it adds, and what it does on your machine (the port it opens, who can connect, approvals answered from a device, the home channel, `ffmpeg`, firmware downloads, the files it writes and the Hermes services it uses). This prepares it for the Hermes plugin catalog.
- A question from the agent (the `clarify` tool) is spoken on devices that speak replies, with its choices read out by number, as well as shown as text. It used to arrive as text only, so a voice user heard nothing while the agent waited for an answer. The next spoken or typed message answers it, as before. Contributed by Antonio Lourenco (@tozes).
- `battery_log: true` in the gadget platform's `extra` keeps each paired device's battery readings (voltage, percent, charging, USB power) in a CSV under the plugin's data directory, a row every 30 seconds, to calibrate a board's battery percentage from a full discharge. Off by default. Contributed by Antonio Lourenco (@tozes).
- Spoken replies stay paced after the text-to-speech producer pauses. A sign error in the hub's stall handling let the rest of a reply go out in one burst after the first pause, which could overflow a device's speaker buffer. A fake-clock test now holds every frame within the playback lead, before and after a stall.
- Enrollment by unapproved devices is bounded: at most 16 may wait to be paired, 4 per network address, and an unapproved record expires an hour after the device's last contact. `hermes gadget pair --yes` approves blindly only when one device is waiting; `hermes gadget pair <device>` picks one. `hermes gadget devices` marks devices still waiting to pair.
- `hermes gadget forget` takes effect on a running gateway. The device store re-reads `devices.json` before every operation and writes through a per-process temporary file, so the gateway no longer keeps a stale copy of a forgotten key or writes it back when the device reconnects.
- The plugin checks, before the gateway creates the adapter, that this Hermes still has every module and private adapter hook it relies on, and fails with a message naming what is missing and the Hermes commit it was tested against. The tested commit lives in `plugin/compat.py`, and a test keeps it equal to the CI pin.
- A too-short utterance no longer leaves the device on "Sending..." until its three-minute timeout. The server now sends its "Didn't catch that" notice and a cancelled `turn.end`, so the device returns to ready at once. On touch devices the notice names the screen instead of the button.
